# Friction Log

Every entry records something that did not work the way the documentation, tooling, or program said it would, what it cost, and how HomeLedger routed around it. Entries are numbered in the order they were hit. Where a friction point drove a design decision, the decision is named so the two can be read together with the [design spec](docs/superpowers/specs/2026-09-13-homeledger-design.md).

Format per entry: **Area** · **Expected** · **Actual** · **Impact** · **Workaround / decision** · **Source** · **Status**.

## Design phase (2026-09-13)

### FL-001 · Alexa+ · MCP Toolkit access is gated, and the request path is not discoverable
- **Expected:** The MCP Toolkit quickstart reads as self-serve: install `@alexa-ai/cli`, run `alexa-ai new mcp`, deploy, test in the web simulator.
- **Actual:** The docs home says the Category SDK and MCP Toolkit are "available to select partners only." The development-stages page says "you request access to the Private Preview" and links no form. The Alexa+ for Builders landing page has no request button. An established skill developer (AnyList) reported a rejected request. The Devpost organizer wrote that entrants "will have no way to actually call Alexa+ anyway."
- **Impact:** A day of reading three pages that disagree about whether a developer can start. No way to test against the real client.
- **Workaround / decision:** Build the MCP server to the published client contract and drive it from a simulated Alexa+ web experience with our own agent, which the organizer confirmed is acceptable. Design section 1 and 7.
- **Source:** https://developer.amazon.com/docs/alexaplus/add-ons/home.html · https://developer.amazon.com/docs/alexaplus/add-ons/alexa-plus-add-on-development-stages.html · https://amazonappdev2026.devpost.com/forum_topics/45058-clarification-on-simulated-alexa-web-experience-requirements
- **Status:** Open. Asked on the Devpost forum whether hackathon entrants can get dev-stage access.

### FL-002 · Alexa+ · Authentication docs contradict each other and the MCP spec
- **Expected:** One documented location for OAuth protected-resource metadata and a spec-conformant 401.
- **Actual:** The quickstart says to host metadata at `/.well-known/oauth-authorization-server`; the account-linking page says `/.well-known/oauth-protected-resource`. The auth page says 401 responses carry no `WWW-Authenticate` header and that Dynamic Client Registration, Client ID Metadata Documents, and OIDC are all unsupported, which is the opposite of the MCP 2025-11-25 authorization guidance the hackathon links.
- **Impact:** Cannot tell which discovery path a real Alexa+ client would follow.
- **Workaround / decision:** Let AgentCore Runtime own the resource-server surface. It serves protected-resource metadata and a spec-conformant 401 with `WWW-Authenticate` on its own invocation URL, so the server code does not have to pick a side. Design section 4.5.
- **Source:** https://developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-quickstart.html · https://developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-account-linking.html · https://developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-authentication.html
- **Status:** Open. Feature request filed.

### FL-005 · MCP spec · The hackathon's minimum version and the current version disagree on fundamentals
- **Expected:** Implementing the linked 2025-11-25 Streamable HTTP page would be current.
- **Actual:** The 2026-07-28 revision removed protocol sessions and the `Mcp-Session-Id` header, removed the `initialize` handshake, replaced server-initiated elicitation with multi round-trip requests, removed SSE resumability, and moved tasks into an extension. The TypeScript SDK v2 (stable line) implements 2026-07-28; v1.x is in maintenance.
- **Impact:** A server written to the hackathon's linked pages is a legacy server on day one.
- **Workaround / decision:** SDK v2 with a modern stateless branch and a sessionful legacy branch from one server factory. Design section 4.1. Week-1 spike validates the legacy branch on AgentCore before building on it.
- **Source:** https://modelcontextprotocol.io/specification/2026-07-28/changelog · https://ts.sdk.modelcontextprotocol.io/v2/serving/legacy-clients.html
- **Status:** Resolved by decision; spike pending.

### FL-006 · MCP TypeScript SDK · Sessionful legacy support is documented as a compatibility posture, not a path

- **Workaround / decision:** Use it anyway, with contract tests driving both the v2 and v1 clients. Fallback to SDK v1.x if the spike fails. Design section 9 and 12.
- **Source:** https://ts.sdk.modelcontextprotocol.io/v2/serving/legacy-clients.html · https://ts.sdk.modelcontextprotocol.io/v2/servers/input-required.html
- **Status:** Open; spike pending.

### FL-017 · MCP SDK · Elicitation spike confirms architecture A with no code changes from the documented shape
- **Expected:** A multi round-trip tool handler written once against `@modelcontextprotocol/server` (`inputRequired`/`acceptedContent`, keyed off `ctx.mcpReq.inputResponses`) would deliver `elicitation/create` to a 2026-07-28 client directly, and the SDK's documented legacy shim would deliver the same request to a 2025-era client over its `NodeStreamableHTTPServerTransport` session, without any transport- or era-specific handler code.
- **Actual:** Confirmed on both generations on the first run, with the `dev.ts`/`server.ts` code exactly as drafted (no fallback to the JSON-Schema `requestedSchema` form, no `ctx.mcpReq` field-name correction). The modern test drives `echo_confirm` through `StreamableHTTPClientTransport` from `@modelcontextprotocol/client` with `client.setRequestHandler('elicitation/create', ...)` and gets one `elicitation/create` round trip per call, matching `inputRequired.maxRounds: 3`. The legacy test drives the same tool through `createApp`'s session-based route (`src/legacy.ts`, `NodeStreamableHTTPServerTransport`) using `@modelcontextprotocol/sdk` 1.30.0's `Client` and `ElicitRequestSchema`, and the server-side default-on legacy shim (`ServerOptions.inputRequired.legacyShim`, default `true`) converted the same `inputRequired(...)` return into a real server→client `elicitation/create` request over the session, re-entering the handler with the answer on retry — with zero legacy-aware code in `dev.ts`. Versions: `@modelcontextprotocol/server` 2.0.0, `@modelcontextprotocol/client` 2.0.0, `@modelcontextprotocol/sdk` 1.30.0 (`pnpm ls @modelcontextprotocol/server @modelcontextprotocol/sdk`).
- **Impact:** None — this is the positive result the whole Plan 1 architecture (and Plan 2's `book_service`) is staked on: one handler, one code path, both client generations, including decline handling (no re-ask) and the `devTools` gate.
- **Workaround / decision:** None needed. Architecture A stands as designed; no addendum task to build a v1-flavoured `server-v1.ts` fallback (architecture C) is opened.
- **Source:** `apps/mcp-server/src/tools/dev.ts` · `apps/mcp-server/test/elicit-modern.test.ts` · `apps/mcp-server/test/elicit-legacy.test.ts` · `node_modules/@modelcontextprotocol/server/dist/createMcpHandler-CLhGwQTn.d.mts` (`ServerOptions.inputRequired`, `inputRequired`, `acceptedContent`) · `node_modules/@modelcontextprotocol/client/dist/index.d.mts` (`ClientOptions.inputRequired`, `.versionNegotiation`)
- **Status:** Resolved. Spike passed; no further action.

### FL-018 · Terraform CLI · `output -raw` exits 0 with a warning when the state has zero outputs, not just when one output is missing
- **Expected:** The deploy workflow's bootstrap guard, `if ! terraform output -raw ecr_repository_url >/dev/null 2>&1; then <targeted apply>; fi`, would fail (non-zero exit) on a brand-new state that has never been applied, so the guard's `then` branch would run and create the ECR repository the image build depends on.
- **Actual:** On a state with zero outputs defined at all (nothing has ever been applied), `terraform output -raw NAME` prints `Warning: No outputs found` to stderr and exits **0**, the same as a successful lookup — it does not exit non-zero the way it does when the state has *other* outputs but not the named one. Run 34882037117 hit exactly this: the guard's condition was true (`>/dev/null 2>&1` succeeded), so the bootstrap `terraform apply -target=aws_ecr_repository.mcp ...` was skipped entirely. Nothing was created — no ECR repository, no state object, no table. The next step, `REPO=$(terraform -chdir=infra/live/demo/platform output -raw ecr_repository_url)`, then also printed the same warning and captured an empty string, and `scripts/build-image.sh` failed immediately with `line 3: 1: usage` because `REPO_URL="${1:?usage: build-image.sh <ecr-repo-url> [tag]}"` saw an empty positional argument.
- **Impact:** The entire first deploy run failed at "Build and push image" before any AWS resource existed; the apply job never reached `terraform apply` for the full plan.
- **Workaround / decision:** Replaced the exit-code guard with a state-membership check, `if ! terraform state list 2>/dev/null | grep -qx 'aws_ecr_repository.mcp'; then <targeted apply>; fi`, which only depends on whether the resource is actually in state and is unaffected by `output`'s exit-code behavior. Also set `terraform_wrapper: false` on every `hashicorp/setup-terraform@v3` step in `deploy.yml` so later `$(terraform output -raw ...)` captures (image repo URL, invocation URL, Cognito values) are reading Terraform's own stdout directly rather than through the wrapper's JSON-log proxy.
- **Source:** https://github.com/jkarns87/homeledger/actions/runs/34882037117 · https://developer.hashicorp.com/terraform/cli/commands/output
- **Status:** Resolved.

### FL-019 · AWS account · Bedrock reported suspended after new-account verification failed
- **Expected:** After account creation on 2026-09-14 and the morning's verification hold clearing (first invocations of Claude Sonnet 4.6, Nova Lite, and Titan Embeddings v2 all succeeded that afternoon), Bedrock would stay available for the hackathon build.
- **Actual:** AWS notified that new-account verification failed and that Bedrock was suspended on account `<account-id>` the same day. Support case 178941623300459 was opened at 2026-09-14T20:03Z as the root user under Account → Other Account Issues; the Basic support plan only allows severity "General question", so no expedited path exists. At about 20:15Z, root-session checks still returned completions from `us.amazon.nova-lite-v1:0` and `us.anthropic.claude-sonnet-4-6`, and the AgentCore control plane listed runtime `demo_homeledger_mcp` as READY, so the scope or timing of the suspension is unclear from the API side. At about 20:35Z the same checks run from GitHub Actions as the OIDC deploy role (run 34894134737) also succeeded for both models and listed the runtime READY, so no principal was observed blocked at that time.
  Two days later the block was confirmed, and it is narrower than "Bedrock is suspended" suggests. On 2026-09-16 the same deploy-role probe (run 35103741472) returned, for BOTH models, `ValidationException ... Error 002: Access to Bedrock models is not allowed for this account`, while the AgentCore control plane in the same run still listed `demo_homeledger_mcp` as READY. So the restriction applies to model invocation only: the AgentCore data plane, DynamoDB, Cognito, ECR, S3, and IAM are all unaffected, and the deployed MCP server keeps serving every tool that does not call a model. The suspension therefore took effect some time AFTER 2026-09-14T20:35Z, which is why the probes that evening came back clean.
  Re-probed a second time the same day at 2026-09-16T17:21Z (run 35127676347) to check whether the block was transient. It is not: both models returned the byte-identical `Error 002` string, and `demo_homeledger_mcp` was still READY in the same run under the same role. Two independent probes hours apart, identical results, so the state is stable rather than flapping — worth knowing before spending any more time re-checking, and the reason the remaining blocked work is deferred rather than retried on a timer.
- **Impact:** Narrower than first feared, and narrower again than this entry originally said — **creating the Knowledge Base was never blocked.** The module applied cleanly on the first post-merge deploy of Plan 2 (merge `0174612`): bucket, Knowledge Base, data source, S3 Vectors index, and IAM role all exist, because nothing in the apply path invokes a model. What is blocked is the ingestion job, whose first act is to have the Knowledge Base role call the Titan embedding model. FL-032 records that correction and what it cost. Blocked: running an ingestion job, `ask_manual` against a populated index, the Strands agent in the simulator, and Nova vision for snapshot descriptions. NOT blocked: every tool the deployed server exposes today, the entire in-memory development path, all Terraform authoring and offline validation, and the Bedrock adapter itself, which is unit-tested against a stubbed sender rather than a live call. Submissions close 2026-10-23 and judging runs 2026-11-09 to 2026-11-20, and the organizers expect resources to be live only for test windows, so an outage in mid-September costs nothing provided it clears before the video and the judging window.
- **Workaround / decision:** Keep building. The design already isolates every model call behind an interface with an in-memory implementation — `ManualRetriever` has a fixture adapter, the repository has an in-memory twin — so development continues at full speed without Bedrock. Only two things wait on it: the manuals ingestion run and the smoke assertion that `ask_manual` returns a real passage. The Knowledge Base apply was listed here as a third and should not have been — it went through on the first attempt (FL-032). Re-probe with the `aws-oidc-check` workflow rather than a local session, since that path needs no local credentials and survives session expiry. The case did not stall — it was closed without resolution, see below. aws-verification@amazon.com is the address AWS's own verification error names. Note that case status cannot be read via the Support API at all on a Basic support plan, so the console is the only view.
- **Source:** AWS Support case 178941623300459 · https://github.com/jkarns87/homeledger/actions/runs/34890188789 (smoke run during the report) · https://github.com/jkarns87/homeledger/actions/runs/34894134737 (deploy-role probe, clean) · https://github.com/jkarns87/homeledger/actions/runs/35103741472 (deploy-role probe, block confirmed) · https://github.com/jkarns87/homeledger/actions/runs/35127676347 (deploy-role probe, block stable on re-check) · https://github.com/jkarns87/homeledger/actions/runs/35353681391 (deploy-role probe after the case closure, still blocked) · `.github/workflows/aws-oidc-check.yml` (the probe itself: `bedrock-runtime converse` on both models plus `bedrock-agentcore-control list-agent-runtimes` in the same run)
- **Second-order friction — the case is unreadable to the tooling that needs it.** Confirming the block took one dispatched workflow and about ninety seconds. Confirming whether AWS has *acted* on it is not possible from any automated path: the Support API requires a Business or Enterprise plan and the account is on Basic, so `aws support describe-cases` is unavailable at exactly the severity tier where a blocked builder most needs it. The deploy role deliberately carries no `support:*` permission, and widening a CI role's blast radius permanently to read one case was rejected as a bad trade. So the loop is asymmetric: the machine can verify the symptom indefinitely but a human must open the console to learn the cause's status. For a hackathon on a new account — precisely the population most likely to trip new-account verification — that asymmetry is the friction, more than the block itself.
- **Case closed without resolution, on a quota rationale that does not fit the symptom (2026-09-18).** AWS closed case 178941623300459, the stated reason being that hackathon-style projects should fit within the beginner quota. That answer conflates two different failures, and the error shape is what tells them apart:
  - A **quota** limit throttles. The invocation is permitted and succeeds, just not as often or as concurrently as asked, and it surfaces as `ThrottlingException` or `ServiceQuotaExceededException` on a request that is otherwise valid.
  - What this account returns is `ValidationException ... Error 002: Access to Bedrock models is not allowed for this account`. That is zero access, not limited access. Whether the beginner quota is generous enough for this project is true and irrelevant — nothing is being consumed against it, because no invocation is permitted at all.

  Three observations make the distinction verifiable rather than an assertion, and they are the reusable part of this entry:
  1. **Two unrelated principals fail identically.** The GitHub OIDC deploy role calling `bedrock-runtime converse` on `us.amazon.nova-lite-v1:0` and `us.anthropic.claude-sonnet-4-6` (`.github/workflows/aws-oidc-check.yml`), and the Bedrock Knowledge Base *service* role calling `amazon.titan-embed-text-v2:0` during `StartIngestionJob` (FL-032) — byte-identical `Error 002` string from both. A quota ceiling on an account's own usage does not manifest as an access denial to a service role invoking an embedding model on that account's behalf.
  2. **It worked, then stopped, with no change in usage.** First invocations of Claude Sonnet 4.6, Nova Lite, and Titan Embeddings v2 all succeeded on 2026-09-14, and the deploy role was still getting completions at 20:35Z that evening (run 34894134737). Access was revoked after that, coinciding with new-account verification failing. Call volume across that boundary was a handful of requests — nowhere near any limit, beginner or otherwise. Quotas do not revoke retroactively on an unchanged workload.
  3. **Only model invocation is affected.** AgentCore's control and data planes, DynamoDB, Cognito, ECR, S3, S3 Vectors, and IAM have all worked continuously throughout — including in the same workflow runs that record the Bedrock failures, where `list-agent-runtimes` returns `demo_homeledger_mcp` READY in the step immediately after the two refused `converse` calls. Quota exhaustion is per-service and per-metric; an account-level access revocation is exactly this shape.

  Re-probed after the closure on 2026-09-18 (run 35353681391): still blocked, both models, same `Error 002` string, with `demo_homeledger_mcp` READY in the same run under the same role.
- **Next step:** request restoration of Bedrock model access following the failed new-account verification, filed under **account verification** rather than under a service-limit or quota category. Filing it as a limit request is what produced the quota answer — the request is not for more capacity, it is for the access that was withdrawn. `aws-verification@amazon.com` is the address AWS's own verification error names, and the distinction above is the substance to lead with.

### FL-032 · Bedrock Knowledge Base · A Knowledge Base provisioned under an account-level model block cannot ingest OR retrieve, because query embedding needs the same model — so infrastructure-as-code reports success for a resource that cannot do its job at all
- **Expected:** Two things, both wrong. First, per FL-016 and FL-019, that the Knowledge Base apply was itself blocked — every earlier entry, several code comments, and the README all assumed "Bedrock is blocked" meant the `aws_bedrockagent_knowledge_base` resource could not be created, which is why the module was described as "authored, never applied" and the smoke's `KNOWLEDGE_BASE_ID` was expected to stay empty. Second, that `KNOWLEDGE_BASE_ID` being non-empty is a sufficient test for "real retrieval is available," which is the assumption both skip paths were built on.
- **Actual:** Plan 2 merged as `0174612` and `deploy.yml` applied cleanly, Knowledge Base module included. The S3 manuals bucket, the Bedrock Knowledge Base, and the knowledge-base IAM role all exist. The apply was never blocked. **That corrects the record in FL-016 and FL-019, and it is now proven rather than assumed** — the control plane creates the Knowledge Base, its data source, and the S3 Vectors index without ever invoking a model, so nothing in the apply path touches the thing the account block refuses.
  The block moves one step later, to the first operation that does invoke a model. Smoke run 35238251562 failed at `seed:manual`: the S3 upload of the fixture PDF and its `.metadata.json` sidecar succeeded, and `StartIngestionJob` then returned `ValidationException ... Knowledge base role arn:aws:iam::<account>:role/demo-homeledger-knowledge-base is not able to call specified bedrock embedding model arn:aws:bedrock:us-east-1::foundation-model/amazon.titan-embed-text-v2:0: Error 002: Access to Bedrock models is not allowed for this account (Service: BedrockRuntime, Status Code: 400)`, HTTP 400. Starting an ingestion job makes the Knowledge Base role call Titan to embed, and that invocation is refused by the same account-wide block FL-019 records (support case 178941623300459, still unresolved). Note the `Error 002` string is byte-identical to the one the deploy-role probes returned in FL-019 — same block, reached through a different caller.
  So a Bedrock Knowledge Base under an account-level model block is **provisioned, addressable, referenced by the runtime, and permanently empty.** `terraform apply` is green, `terraform output -raw knowledge_base_id` returns a real id, the AgentCore runtime carries that id in its environment, and not one document can ever be embedded into it.
- **Impact:** The damage was not the failed ingestion — that was expected collateral of FL-019. The damage was that **one blocked embedding call hid all eight working tools.** Both skip paths in this repo keyed off a binary "is a Knowledge Base provisioned," read as `KNOWLEDGE_BASE_ID != ''`: the workflow used it to decide whether to run `seed:manual` at all, and `scripts/smoke.ts`'s `checkManualPassages` used it to decide whether to enforce the `ask_manual` assertion. With the Knowledge Base now provisioned, that condition is true, so neither skip fired; `seed:manual` exited 1 on the `StartIngestionJob` rejection, the step failed, and the workflow never reached `Run smoke`. Tool order, widget wiring, the FL-023 appliance-count guard, elicitation through the legacy shim, three-round `book_service`, progress notifications, `get_visit` — none of it ran. A run that should have proved eight of nine tools healthy proved nothing at all, and the first post-merge signal on a working deploy was a red X.
  The general finding, and the reason this is worth a friction entry rather than a bug fix: **"is it provisioned" is the wrong abstraction.** Provisioning and usability are separate properties, and infrastructure-as-code only reports the first. Any resource whose usefulness depends on a capability outside its own creation path — a Knowledge Base that needs model invocation, a KMS-encrypted bucket whose key policy is managed elsewhere, a VPC endpoint whose service is not enabled in the account, a queue subscribed to a topic in a suspended region — can be created successfully and still be incapable of its job. Tooling that models two states (absent / present) has nowhere to put the third (present but unusable), and the failure mode is not a wrong answer but no answer: the check that was supposed to degrade gracefully instead takes down everything downstream of it.
- **Workaround / decision:** Model the third state explicitly, in both places it bites, without weakening either real guard.
  1. `scripts/manuals.ts` grew `isBedrockAccountBlock(error)`, which requires all three of: `name === 'ValidationException'`, `$metadata.httpStatusCode === 400`, and a message containing the exact sentence `Access to Bedrock models is not allowed for this account`. Duck-typed on `name` rather than `instanceof`, per AWS's own v3 error-handling guidance, since each client bundles its own copy of the exception class. The sentence is the match because it is the only part of the message that states the condition; the role ARN, the model ARN, the `Error 002` code, and the `(Service: ..., Status Code: ...)` suffix are all excluded deliberately as account-, model-, region- and wrapper-specific noise that would make the matcher break on changes unrelated to the condition. It is scoped to the `StartIngestionJob` call only — not to terminal `FAILED` statuses, and explicitly **not** a blanket catch of `ValidationException`, which `StartIngestionJob` also raises for a malformed metadata sidecar, an S3 key outside the data source's inclusion prefix, and a `dataSourceId` that does not belong to the knowledge base. All of those are real bugs in this repo and all still fail the run. On a match `uploadManual` returns a discriminated `{ ingestion: 'skipped-bedrock-blocked' }` result, `seed:manual` prints a loud banner plus a bare `MANUAL_INGESTION_SKIPPED` sentinel line, and exits 0.
  2. The uploaded S3 objects and the `DOC#` row are **kept, not rolled back.** The PDF and its sidecar are exactly the input a later ingestion job consumes, so once the block clears a bare `StartIngestionJob` picks them up with no re-upload; the `DOC#` row is what `get_appliance` reads for `{docId, title}` and what `appliance.manualDocId` points at, so deleting it would remove working functionality in reaction to an unrelated external outage. The row stays honest — `kbSync.status` is left at `'pending'` with `at: null`, which is the accurate description of uploaded-but-not-ingested, and is why this is kept state rather than orphaned residue. Contrast the appliance-not-found guard in the same function, which deliberately writes nothing because that error is permanent and operator-caused; this one is transient and external. `derivedId` keeps `docId` and `s3Key` deterministic, so a re-run replaces in place — the duplicate-accumulation risk that would otherwise argue for cleanup does not exist here.
  3. `scripts/smoke.ts`'s `checkManualPassages` now returns one of three outcomes instead of two. The distinction that matters is between "ingestion was skipped" and "ingestion happened and returned the wrong content," and **those are indistinguishable from the retrieval side by construction** — a never-ingested Knowledge Base and a runtime quietly serving `SAMPLE_MANUAL_PASSAGES` both come back as "no passage carries `SMOKE_MANUAL_TITLE`." Inferring the skip from an empty or fixture-shaped result would therefore reintroduce exactly the false green the assertion exists to prevent. The signal is instead carried in from the step that knows: `.github/workflows/smoke.yml` greps `^MANUAL_INGESTION_SKIPPED$` out of the seed step's log and exports `MANUAL_INGESTION_SKIPPED=1`, the same log-sentinel idiom as the `grep -q '^SMOKE OK$'` gate. `manualIngestionSkipped()` accepts only `1`/`true`/`yes`, so unset, empty, `0`, `false`, and anything unrecognised all mean "enforce" — the skip is opt-in by exact value, and a mistyped signal produces a red pipeline rather than a green one that proves nothing.
  4. `continue-on-error` was explicitly **not** used as the mechanism on the seed step. It would have swallowed the malformed-sidecar, bad-key, missing-data-source, and unrelated-IAM cases alongside the one condition worth tolerating, which is the opposite of the point. The step is a plain `run:` under bash's `-eo pipefail`, so any non-zero exit from `seed:manual` still fails the job.

  **The generalisation, and the bit worth taking away from the whole entry:** a capability dependency does not stop at the operation that obviously needs it. ### FL-033 · Claude Code MCP client · It negotiates 2025-11-25 and answers elicitation the 2025 way, so the "modern clients use multi round-trip requests" assumption is wrong for the one client a person actually has — and a naive stdio-to-HTTP proxy deadlocks on the first question rather than failing
- **Expected:** The 2026-07-28 revision replaced session-based elicitation with multi round-trip requests (MRTR): the server answers `tools/call` with `resultType: 'input_required'` plus a signed `requestState`, and the client re-calls with `inputResponses`. `book_service` is written to that shape (FL-024, FL-025), and the working assumption behind this plan's bridge task was that a current client would drive it that way — which would make a stdio-to-HTTP bridge almost trivial, because MRTR is stateless per request: every round is an independent POST with its own complete response, needing no session affinity, no server-initiated messages, and no overlapping requests.
- **Actual:** Claude Code 2.1.56 does none of that. Read out of its own bundle (`/opt/homebrew/lib/node_modules/@anthropic-ai/claude-code/cli.js`, build 2026-02-25): `LATEST_PROTOCOL_VERSION` is `"2025-11-25"` and `SUPPORTED_PROTOCOL_VERSIONS` is `["2025-11-25", "2025-06-18", "2025-03-26", "2024-11-05", "2024-10-07"]` — **`2026-07-28` is absent.** The MRTR vocabulary is absent with it: `inputRequests`, `inputResponses`, `requestState`, `allowInputRequired` and `maxRounds` occur **zero** times in the bundle. What is present is `elicitation/create` (3 occurrences), in both `form` and `url` modes, with `notifications/elicitation/complete` and `elicitationId` for the 2025-11-25 async extension. One trap for anyone repeating this grep: `input_required` DOES appear twice, but as a **task status** in the 2025-11-25 tasks extension (`["working","input_required","completed","failed","cancelled"]`), not as MRTR's `resultType` — the string matches and means something else entirely. Two further findings from the same read. First, the elicitation capability is gated: the client is constructed as `new Client({name:'claude-code',...},{capabilities:{roots:{},...(O?{elicitation:{form:{},url:{}}}:{})}})` where `O` resolves to the GrowthBook feature `tengu_mcp_elicitation`, **default false**, with no environment or settings override anywhere in the bundle. On this machine it is currently `true` (`~/.claude.json` → `cachedGrowthBookFeatures.tengu_mcp_elicitation`, cached 2026-09-18T07:44) — so `book_service` can ask its questions here, but that is a remotely-controlled flag, not a property of the client, and an owner for whom it is off gets `Error: Client does not support elicitation` instead of a conversation. Second, stdio servers are spawned with `env: {...process.env, ...q.env}`, so a bridge inherits the environment Claude Code itself was launched with. Confirmed all of this against the real server, not just by reading: a 1.30.0 `Client` carrying Claude Code's exact name and capability set, pointed at `createApp()` over a real socket, negotiated `2025-11-25`, was issued an `Mcp-Session-Id` (i.e. routed to `src/legacy.ts`'s shim, not the modern handler), and received three `elicitation/create` requests in `form` mode plus progress `0,1,2,3`.
- **The part that matters for a proxy.** An HTTP-level trace of that session shows why a naive bridge does not merely misbehave, it hangs. The `book_service` `tools/call` POST answers `200 text/event-stream` and **stays open**; the three `elicitation/create` requests arrive on that POST's own stream (not on the standalone `GET` stream, which is opened and stays idle all session); and each answer goes back as a **separate POST** that must be sent *while the first one is still open*, each returning `202`. The call's own response only completes after the third answer. So the two properties a bridge must have are: (1) relay the response body as events arrive — `await res.text()` on that POST waits for a stream that is waiting for an answer that cannot be sent until the stream is read, which is a deadlock, not an error; and (2) let requests overlap — a read loop that awaits each message before reading the next deadlocks identically. Both are the tidy-looking implementation. Neither fails loudly; both hang.
- **Impact:** Positive on balance, and it reframed the task. The bridge needed to be a *transport* relay rather than an MCP client/server pair: it parses each JSON-RPC message only far enough to re-serialise it onto one line, capture the negotiated version, and know which ids need an error answer. It never reads a method, so `elicitation/create`, `notifications/progress`, MRTR and anything a later revision adds all ride the same path. The larger consequence is for the Alexa+ track: the documented Alexa+ client is a 2025-era client, and the client that ships to millions of developers turns out to be one too, so the legacy shim this plan built (FL-025) is not a compatibility gesture for an old client — it is the path every real client currently takes. ### FL-037 · Terraform + AWS Secrets Manager + GitHub Actions · The documented cost-control lever had no shipped way to pull it, and the default that would have made pulling it a one-way door was invisible because it was never written down
- **Expected:** `docs/RUNBOOK.md` §11 described a clean cost-control story for the gap between hackathon test windows: apply with `image_uri=""`, the AgentCore runtime goes, everything else stays, and one `gh workflow run` brings it back. The Terraform genuinely supports that — `count = var.image_uri == "" ? 0 : 1` is on the runtime resource and on nothing else, so the blast radius is exactly one resource. Two things should follow: that some workflow can pass the empty value, and that the round trip is symmetrical.
- **Actual: neither followed, and the two failures are opposite in kind.**
  1. **The lever was unreachable.** `deploy.yml`'s `apply` job always computes `IMAGE` from `scripts/build-image.sh` and passes `-var "image_uri=$IMAGE_URI"`; its `workflow_dispatch` trigger declared no `inputs:`; there was no destroy workflow in `.github/workflows/`. The one place `-var image_uri=""` appeared was the ECR bootstrap step, `-target`ed at two resources and guarded on `aws_ecr_repository.mcp` being absent from state, so it could not touch the runtime. The documented path was correct about the Terraform and impossible to execute.
  2. **The round trip was a one-way door, and nothing said so.** Neither `aws_secretsmanager_secret.request_state` (platform root) nor `aws_secretsmanager_secret.this` (`cognito-m2m`) set `recovery_window_in_days`, so the AWS provider's default of **30** applied. A destroy therefore *schedules* a secret rather than deleting it, and a scheduled secret keeps its **name** reserved for the whole window. Re-applying the stack with the same names inside those 30 days fails with `InvalidRequestException: You can't create this secret because a secret with this name is already scheduled for deletion`. Tear the demo down in October and it cannot come back for judging on 2026-11-09 without renaming the secrets or a manual `restore-secret` plus `terraform import`.
- **Why the second one is the interesting half.** The first is an absence: a workflow that does not exist is at least visibly missing the moment somebody tries. The second is a **default that is invisible at the call site**. `resource "aws_secretsmanager_secret" "this" { name = var.secret_name }` is three words long and reads as complete. Nothing in it says "and a destroy of this will block the next apply for a month". The trap is not in the code that was written; it is in the code that was not written, and code that was not written cannot be reviewed. That is the same shape as FL-034/FL-035/FL-036 wearing different clothes — those were "the path that was validated was not the path that was real", this is "the behaviour that was reviewed was not the behaviour that would happen" — and it lands in the same place: every check the project runs was green, because no check the project runs destroys anything.
- **Impact:** Bounded, because it was found before a teardown rather than after one. Had it not been, the cost would have landed precisely in the judging window (2026-11-09 to 2026-11-20) as an unrecoverable-looking apply failure, on the one day the stack has to work. The documentation cost was already paid: §11.2 shipped with three ranked workarounds for a missing capability, §11.4 with a recovery procedure for a trap that did not need to exist.
- **Workaround / decision — a dispatch-only workflow whose blast radius is structural, plus the window closed at both resources.**
  - **`.github/workflows/teardown.yml`**, `workflow_dispatch` only, two modes. `teardown-runtime` requires the `confirm` input to be exactly `destroy demo runtime`, checked in a **failing step** rather than a job-level `if:` — a skipped job reports green, and green is the wrong answer to "you did not confirm". The typed value reaches the shell through `env:` rather than `${{ }}` interpolation, because a job holding AWS credentials is the wrong place for a script-injection hole.
  - **The scope is the mechanism, not a policy on top of it.** The job runs `terraform apply -var image_uri=""`. No `terraform destroy`, no `-target`, no input that widens it. Putting those behind a scarier confirmation string in the same dispatch menu would make the dangerous operation exactly as easy to reach as the routine one. A full destroy stays an out-of-band act by a human holding credentials, and §11.4 is where it is written down.
  - **Bring-up is its own path, and it is not a second copy of `deploy.yml`.** A plain `gh workflow run deploy.yml` does work after a runtime-only teardown — the ECR bootstrap guard is skipped because the repository is still in state, and build-and-push supplies a fresh `image_uri` — and it stays the documented fallback. `bring-up` builds nothing and pushes nothing: it redeploys an image **already in ECR**, by default the one teardown recorded in its run summary before the destroy (afterwards `deployed_image_uri` is `""` and the tag is gone from state). So what comes back is the artifact that was torn down rather than a fresh build of whatever `main` holds today, in seconds rather than minutes. It refuses, with an instruction, when there is no ECR repository in state (that is a first deploy, and `deploy.yml` owns the bootstrap) or no tagged image in it.
  - **`recovery_window_in_days` set on both secrets, with the warning at the line.** The module is reusable — `infra/modules/cognito-m2m` has its own README, variables and tests, and is the thing somebody copies — so it takes `var.recovery_window_in_days` defaulting to **30**, AWS's own default and the production-safe answer, validated to `0 || 7..30` because AWS rejects 1-6. `infra/live/demo/platform` is what opts in, through `var.secret_recovery_window_in_days` (default `0`), passed to both its own secret and the module. The demo gets the round trip; a copied module gets the recovery window; and a non-demo copy of the root sets one number in one place to get production semantics back. Both resources carry the warning in a comment at the resource, not only in a doc, because a future reader copying this into something real has to meet it at the line.

### FL-038 · Amazon Bedrock AgentCore Runtime · The runtime's id is generated at create time and the service has no alias layer of any kind, so a teardown scoped to exactly one resource invalidated every invocation URL ever issued
- **Expected:** FL-037 shipped `teardown.yml` on the strength of a blast radius of exactly one resource: `count = var.image_uri == "" ? 0 : 1` is the only conditional in the configuration, so an apply with an empty `image_uri` destroys the AgentCore runtime and nothing else. Every identifier the rest of the project is pinned to — the Cognito client id and secret, the Knowledge Base id, the table name, the ECR repository and its images — is on an unconditional resource and survives. `docs/RUNBOOK.md` §11.3 said the round trip changes "one thing", a fresh runtime ARN, and treated that as a re-run of `print-setup`. The round trip was run on 2026-09-21 to prove all of that before judging rather than during it.
- **Actual: the blast radius was exactly as advertised and the consequence radius was everything.** Teardown (run 35615354202) planned and applied `Plan: 0 to add, 0 to change, 1 to destroy` — `Destruction complete after 4m48s`, `Apply complete! Resources: 0 added, 0 changed, 1 destroyed`. Bring-up (run 35616472515) came back in `Creation complete after 5s` by redeploying an image already in ECR, and the smoke that followed (run 35616643237) printed `SMOKE OK` with `book_service` completing three elicitation rounds and `progress 0,1,2,3` in 1807 ms. Every identifier that was supposed to survive did: Cognito client id `3hhkt2a5j155d960s4uircaoqh` and Knowledge Base id `EKF93YIKCK` are byte-identical either side of the destroy, and the seeded household was still there. **The runtime id was not one of them.** AgentCore generates it at create time as a random ten-character suffix, so `demo_homeledger_mcp-093ImbCPE3` became `demo_homeledger_mcp-Rgb4ruHdu7`, and the invocation URL — which is the runtime ARN percent-encoded into the path — moved with it. Every URL and every `claude mcp add` command issued before that moment stopped resolving, silently: the old address does not redirect, it simply names a runtime that no longer exists.
- **And there is nothing in the service to hide it behind, which is the part worth reading.** The `?qualifier=DEFAULT` in the invocation URL is an *endpoint name*, not a version, and the endpoint API is real: `create-agent-runtime-endpoint`, `update-agent-runtime-endpoint`, `list-agent-runtime-endpoints`, plus `list-agent-runtime-versions`. A named endpoint can even be pinned to a version and repointed later, which is a genuinely useful blue/green primitive. It is not an alias. The documented output settles it in one line — `agentRuntimeEndpointArn` has the pattern
  ```
  arn:aws(-[^:]+)?:bedrock-agentcore:[a-z0-9-]+:[0-9]{12}:runtime/[a-zA-Z][a-zA-Z0-9_]{0,47}-[a-zA-Z0-9]{10}/runtime-endpoint/[a-zA-Z][a-zA-Z0-9_]{0,47}
  ```
  — and creation requires `--agent-runtime-id`, itself patterned `[a-zA-Z][a-zA-Z0-9_]{0,99}-[a-zA-Z0-9]{10}`. The endpoint is a **child** of the runtime and inherits the rotating suffix, so it is stable across exactly the thing that was already stable (in-place updates) and gone across the thing that was not (a recreate). A review of the full `bedrock-agentcore-control` command surface, 170+ commands, turned up no alias command, no custom-domain command, and no DNS or ACM binding. The nearest neighbours — `create-registry`, `create-workload-identity`, `create-harness` — are unrelated concerns.
- **The one thing that does rotate is teardown, and routine deploys do not.** Read from `hashicorp/aws` `internal/service/bedrockagentcore/agent_runtime.go`: `RequiresReplace` appears at exactly two sites on this resource — `agent_runtime_name`, unconditionally, and `agent_runtime_artifact`, only when the artifact type flips between `code_configuration` and `container_configuration`. Image URI, environment variables, execution role, description, lifecycle, network, protocol, authorizer and request-header configuration all update in place, and the resource implements `Update` against `UpdateAgentRuntime`, which takes `--agent-runtime-id`, has no `--agent-runtime-name` at all, and returns the same ARN with a bumped version. Confirmed live by run 35623151468 (`Plan: 0 to add, 1 to change, 0 to destroy`, container URI moved, ARN unchanged) and by run 35613845065 sitting at `agent_runtime_version = "14"` on a single ARN — fourteen in-place updates, no rotation. So the September rotation was caused by the `count = 0` destroy/create cycle and by nothing else.
- **Impact:** Bounded, and bounded by luck rather than by design — the round trip was run on 2026-09-21 as a rehearsal, seven weeks before judging opens on 2026-11-09, at a moment when the only addresses outstanding were the owner's own. Run it in early November instead, which is exactly what `docs/RUNBOOK.md` §11.5 used to schedule ("After the window" was a teardown, and the safe minimal state was described as having "every identifier stable"), and the same five seconds of bring-up would have invalidated whatever had been published to judges, with no alias to repoint and no warning anywhere near the lever.
- **What was ruled out, and why — because "put something in front of it" is the obvious answer and it is wrong here.**
  - **A CloudFront distribution or an API Gateway in front of the runtime.** The instinct is to map a friendly host onto a moving origin, but the host is not what moves. `bedrock-agentcore.us-east-1.amazonaws.com` is a stable regional endpoint; the rotating identifier is percent-encoded into the **path** (`/runtimes/arn%3A…%2Fdemo_homeledger_mcp-Rgb4ruHdu7/invocations`). A front door would therefore have to *rewrite a path* on every request, with the current ARN baked into its configuration — which means the proxy has to be redeployed on exactly the events that rotate the ARN. That is not indirection, it is the same coupling with an extra hop.
  - **And the extra hop is the expensive part.** HomeLedger's server is a stateful Streamable HTTP MCP server, and FL-033 already paid for what happens when an unproven intermediary sits in front of that transport: a naive proxy that buffers instead of streaming **deadlocks on the first elicitation question** rather than failing, and the regression tests that catch it time out at 30 s rather than asserting. Putting a fresh, untested hop in front of `book_service`'s three round trips, in the weeks before judging, trades a rotation risk for a deadlock risk — and the deadlock is the one that has actually happened here. API Gateway compounds it with a hard ceiling: an HTTP API's integration timeout maxes out at 30,000 ms and cannot be raised, and a REST API's default 29 s can only be raised at the cost of a Region-level throttle reduction. A long-lived stream through either is severed by the clock.
  - **AgentCore Gateway,** the one native indirection, returns its own `gatewayUrl` from an independently lifecycled resource, so a runtime really could be recreated behind a URL that never moved. Two problems. Its id carries its own ten-character random suffix (`([0-9a-z][-]?){1,100}-[0-9a-z]{10}`), so it relocates the rotation risk rather than removing it — acceptable, since a Gateway has no reason to be torn down. The disqualifying one is that a Gateway is **not a transparent reverse proxy**: it re-exposes targets as MCP tools and resolves the runtime endpoint internally, and `book_service` depends on multi-round-trip elicitation carried in a signed, client-echoed `requestState`. Whether that survives a Gateway is untested, and the expectation is that it does not. Not adopted, and not to be adopted without an end-to-end `book_service` test through it.
  - **A PrivateLink/VPC endpoint** would supply a private DNS name for the regional service *host*, which is already stable, and would leave the path — the thing that rotates — untouched. Reasoned, not tested; listed so nobody spends a day on it.
- **Workaround / decision — stop pulling the lever, and put the reason at the lever.** Do not dispatch `teardown-runtime` again before 2026-11-20. An idle runtime on this stack's serverless microVM path bills per second on actual consumption, and the Terraform resource has no CPU, memory or capacity attribute to reserve; the only non-zero idle line is memory for the life of an open session, about $0.0006 at the 128 MB floor across this stack's 1800 s `idle_session_timeout_seconds`. Weighed against every address a judge holds, the cost argument does not survive contact with the pricing model. Concretely: the warning is now in `.github/workflows/teardown.yml`'s header comment **and** in the `confirm` input's description, which is what the dispatch dialog renders and therefore the last thing an operator reads; `docs/RUNBOOK.md` §11.2 is rewritten so the default recommendation is to leave the runtime running, with teardown still documented and its consequence stated at the top; and `print-setup`'s `ListAgentRuntimes`-by-name discovery stays the supported setup path precisely because it is the only mechanism in reach that *does* survive a rotation. No proxy, no DNS, no named endpoint created in the hope of stability.
- **The generalisable form, and it is the sharper sibling of FL-032's.** FL-032's lesson was to ask how far a capability dependency *reaches* — the Bedrock block reached one step further than the model predicted, twice. This one is about a different axis: **blast radius is not consequence radius.** Every safety mechanism this project built for teardown counts resources — the `count` that makes a wider destroy inexpressible, the plan guard that refuses any delete other than the runtime's address, the post-apply check. All of them were correct, all of them passed, and all of them measure the wrong quantity. A change can touch exactly one resource and still break every consumer downstream of an identifier that resource owns, because the consequence follows the identifier, not the resource. The question a review has to ask alongside "what does this destroy" is **"what names does this destroy, and who is holding them"** — and for any platform-generated id, the follow-up is whether the platform offers an alias layer at all, *before* the id is handed to anyone.

This one says the same thing about diagnostics: the cost of a vague error is no longer a confused human who asks a follow-up question, it is a fluent answer nobody has any reason to doubt. ### FL-040 · Node.js + Debian slim containers · `Intl` with a `timeZone` does not fail when the data is missing — it silently returns UTC, and the validator that was supposed to catch a bad zone goes blind at the same moment
- **Expected:** Localising a stored UTC instant into the household's zone is one line — `toLocaleString('en-US', { timeZone })` — and a runtime that cannot do it says so. A missing or misspelled zone name raises `RangeError: Invalid time zone specified`, which is the documented behaviour and the reason `Intl` looked like a sufficient validator on its own.
- **Actual:** Both halves of that are conditional on the build. A Node compiled `--without-intl` stubs the `Intl` namespace: `new Intl.DateTimeFormat('en-US', { timeZone: 'America/Chicago' })` constructs, `format()` returns a UTC-shaped string, and the `timeZone` option is **ignored rather than rejected**. Reproduced against the deployed image by substituting such a stub: `timeZoneDataProblem()` reports `Intl formatted 2026-01-15T18:30:00.000Z in America/Chicago as "2026-01-15T18:30:00.000Z"`, and in the same breath `isIanaTimeZone('America/Nowhere')` flips from `false` to `true`. There is no exception anywhere on that path. A container built on such an image serves "1:00 PM CDT" for an instant that is 8:00 AM in Chicago, and accepts `Middle/Earth` as the household's zone.
- **And `Intl` is not a sufficient validator even with full ICU.** Verified on Node 22.23.2 and 24.13.1: `{ timeZone: '+05:00' }` constructs and resolves to `+05:00`; `'-0600'` resolves to `-06:00`; `'GMT'` resolves to `UTC`. So the one check that looks like it validates a zone name accepts the exact class of value — a frozen offset — that this feature exists to keep out of the record, because an offset stored in September renders every November visit an hour early once US Central leaves daylight saving.
- **Impact:** Nil in production and that is luck, not design. The deployed base image is `node:22-bookworm-slim`, which carries Node v22.23.2 with ICU 78.2 and 418 zones — checked by building `apps/mcp-server/Dockerfile` for `linux/arm64` and running the compiled `dist/` inside the resulting image, where `speakZonedWindow` returns `Tuesday, September 15, 8:00 AM to 10:00 AM CDT` and the same helper returns `12:00 PM CST` for a November instant. No fix to the image was needed. The cost is entirely in what the failure mode would have looked like had it been needed: nothing throws, nothing logs, the spoken times stay plausible, every unit test on a developer laptop stays green, and the bug is a base-image line in a Dockerfile rather than anything in the diff that introduces it.
- **Workaround / decision — probe for the capability, at startup, and make it fatal.** `packages/core/src/domain/time.ts` exports `timeZoneDataProblem()`, which formats a fixed instant (2026-01-15T18:30Z, chosen so the answer is `12:30 PM CST` — pinning the offset *and* the abbreviation *and* the winter side of the DST boundary) and then, separately, asserts that a nonexistent zone is still rejected. Two probes, because the two failure modes are different: a runtime that cannot apply a zone gets the first one wrong, and a stubbed `Intl` that accepts everything passes the first and fails the second. `apps/mcp-server/src/deps.ts` calls it before it reads any other environment variable and throws on a non-null result, so the container refuses to start with one sentence naming the problem instead of booting and serving wrong clock times. Zone validation does not lean on `Intl` alone either: `isIanaTimeZone` requires a region/location name (or exactly `UTC`) before it ever asks ICU, which is what refuses `+05:00`, `-0600`, `GMT` and `EST`. Both are under test with a stubbed `Intl` rather than asserted against the machine the suite happens to run on.
- **A smaller one in the same family, recorded because it bites tests rather than users.** ICU 72 changed the separator before AM/PM from U+0020 to U+202F, so an expectation of `8:00 AM` compares unequal to a formatter's output on one ICU version and equal on another. Every formatted string is normalised through `normaliseSpaces` before it leaves `voice.ts`. The deployed image emits a plain space today, which means an end-to-end assertion cannot prove the normaliser does anything — it is proved by its own unit test, against strings built with `String.fromCodePoint(0x202f)` rather than written inline, because Prettier rewrites a `\u` escape in a string literal into the invisible character itself.
- **The generalisable form.** FL-039 said an error a model will read has to state what did *not* happen. This is the case where there is no error to read at all: **a capability that degrades instead of failing cannot be detected by calling it and checking for an exception — it has to be detected by calling it and checking the answer.** `Intl`, locale-dependent formatting, crypto with a missing algorithm and any `--without-*` build flag share the shape. The test that separates them is whether the code has an *expected value* to compare against, not merely a call that returns. And the second half: a library's own permissiveness can silently disarm a validator built on it. `isIanaTimeZone` was correct code that returned `true` for `Middle/Earth` the moment ICU went away, because its entire negative case lived inside someone else's `throw`.

#### FL-044 addendum (fix round 1) · The same two lessons, each surviving one step past where they were applied — and a third that contradicts its own obvious reasoning
- **What the first pass got right and still missed.** Both generalisable forms above were correct and neither was carried to the end of its own reach. *"A module's safety property may live in its call site"* was applied to the `log` slot and not to the other two output channels of the same function: `resolveUrl()`'s rejection runs `awsFailureMessage`, which interpolates `err.message` verbatim, and `token()`'s rejection echoes up to 300 characters of the Cognito error body on purpose (`token.ts`'s `MAX_ERROR_BODY`). And *"an assertion over an empty collection passes for the wrong reason"* was applied to the log test and not to the `'use client'` rule one `it` away in the same file, which reads a file set that is empty by construction because no such module exists yet.
- **And the reasoning attached to the fix was false.** The comment claimed the pre-`resolveClientSecret` window "cannot carry a credential, because none has been read yet". `loadConfig` reads `HOMELEDGER_COGNITO_CLIENT_SECRET` into `config.clientSecretFromEnv` **36 lines before** the first lookup. The credential had been read; it had merely not been registered with `protectSecret`. What makes this worth its own line is *why no test could have caught it*: `redact`'s registry is a module-global array that never forgets, so the second `resolveUpstream` in a process is protected by the first one's registration — the leak exists only on the first call in a fresh process, and is masked by its own neighbours in any multi-test file. The fix is one line; the test for it needs its own file, a `resetProtectedSecrets()`, and a precondition assertion that the registry really is empty, or it passes for the wrong reason in exactly the way the entry above warns about.
- **The third one, which is the interesting one, because the obvious reasoning is sound and the conclusion is still wrong.** A credential name assembled at runtime — `process.env['ANTHROPIC' + '_API_' + 'KEY']` — defeats any static name scan. The natural conclusion, and the one first written down here, is that it does not matter: Next's `DefinePlugin` substitutes *literal member expressions* only, so a computed key is never inlined and the value really does resolve to `undefined` in the browser. Every clause of that is true. The conclusion is still wrong, because the value reaches the browser by a different road entirely: a `'use client'` component is **prerendered on the server** at build time, where `process.env` is the real environment, and whatever it renders is written into the HTML that is then served. Built as a real route with `ANTHROPIC_API_KEY=sk-ant-SENTINELKILO999`: nothing in `.next/static` — the DefinePlugin reasoning holds — and `<span>sk-ant-SENTINELKILO999</span>` as literal text in `.next/server/app/built.html`. #### FL-044 addendum 2 (fix round 2) · An exemption is only as narrow as the thing it is matched against — and the concern written in round 1's own report was already true when it was written
- **Expected:** The round-1 rewrite replaced an include-list guard with a root walk plus an exclude list, on the reasoning that an include list fails open and an exclude list fails closed. Round 1's report closed with a concern about exactly this: *"the exclude list now fails closed but grows … a future task adding an exclusion should be made to justify it."*
- **Actual — the instinct was right and the list was already holed when the concern was written.** `EXCLUDED_DIRECTORIES` matched on **basename at any depth**, not at the package root. `test`, `dist`, `e2e`, `coverage` are all exclusion entries and all perfectly ordinary Next route segments, so `src/app/test/page.tsx` — a route serving `/test` — was never opened by the guard at all. Verified end to end: suite fully green, and `ANTHROPIC_API_KEY=sk-ant-SENTINELEIGHTH888` reached `.next/server/app/test.html` as `<span>sk-ant-SENTINELEIGHTH888</span>` plus `test.rsc`. The same bug was in `EXCLUDED_FILES`: `src/lib/playwright.config.ts` would have been skipped too. And a second variant reached the same place by import rather than by path — `src/app/x/page.tsx` importing `../../../test/shared-fixture`, where the resolver hit a file outside the collected set, returned `undefined`, and the walk silently stopped; sentinel confirmed in `x.html` and `x.rsc`.
- **A ninth, found while fixing the eighth, and it is the opposite mistake.** `public/` is copied verbatim to the site root, so every file in it is readable by URL whatever its extension — `public/notes.txt` is `GET /notes.txt`. The guard filtered it by *source-code extension*, which is a question that simply does not apply there: a `.txt`, `.yaml`, `.csv` or `.env` in `public/` is served and was unscanned. Confirmed by planting `public/notes.txt` containing a credential and reading it straight back out of the built package.
- **Impact:** All three are latent rather than live — the committed tree never had a route named `test`, an import into `test/`, or a `public/` directory. The point is that the guard existed specifically to stop the *next* commit doing one of them, and would not have. The eighth is the most likely of the three to happen for real: `/test` is what anyone names a scratch route.
- **Workaround / decision.** (1) Every exclusion is anchored at the package root — an excluded name counts only as a direct child of the root, and nested it is an ordinary directory that gets walked. (2) The scanned region has no silent edges: an import that resolves into an excluded directory is an **offence** (`unscannedImportOffenders`), not a place the walk stops. That direction was chosen over widening the scan because the alternative drags `credentials.test.ts` back into scope and forces the credential rule to be relaxed until it proves nothing — and because the exclusion is *premised* on nothing compiled reaching those directories, so an import that reaches one falsifies the premise and should say so. (3) Inside `public/`, the extension filter is suspended entirely; only binary media are skipped, and that skip is itself asserted in both directions. (4) The list is kept honest **by construction rather than by discipline**: the probe suite iterates `EXCLUDED_ROOT_DIRECTORIES` with `it.each` and plants a credential at `src/app/<name>/page.tsx` for every entry, so a future exclusion is probed the moment it is added and nobody has to remember to write the probe. Un-anchoring the directory check fails 11 tests; un-anchoring the file check, disabling the import rule, and either direction of the `public/` rule each fail their own.
- **And one fix from round 1 was correct but unasserted.** The outer `scrubbed()` on `resolveUpstream` itself — the third of the three output channels — could be removed with 42/42 still green. This is the same shape as the `stack` line caught in round 1 one level down: a fix nothing would notice the absence of. Now asserted, and the mutation recovers `client_secret=not-a-real-secret-value` verbatim from a `resolveUpstream` rejection.
- **The generalisable form.** Round 1's lesson was "sweep the class, not the instance". This is its sharper version: **when you fix a defect by replacing a mechanism, the replacement is a new mechanism and needs its own adversarial pass — the fix does not inherit the scrutiny that found the bug.** The exclude list was written *as* the fix for an include list that failed open, and it shipped with a hole of exactly the same character, in the same commit, written by someone who had just spent an hour thinking about precisely this failure mode. Two concrete tells worth carrying: **any exemption matched by name rather than by path is a hole generator**, because a name is something anyone can create anywhere and every plausible exclusion name is also a plausible directory name; and **a list that grants exemptions should generate its own probes**, because the entry added six months from now will not get a hand-written test. The related tell for the `public/` case: **when a rule is inherited from a neighbouring context, check the question it asks is still the right question** — extension filtering is right for "what does the bundler compile" and meaningless for "what does the server hand over verbatim".

### FL-045 · Task 4 brief's own Step 1 test file · A floating `.then()` on a promise that rejects later in the same test fails the run even though every assertion in it passes
- **Expected:** Task 4's brief gives `apps/simulator/test/elicitation.test.ts` verbatim, including `'reports an answer for a turn it does not hold, and resolves nothing'`, which subscribes to `q.answer` with `void q.answer.then(() => { settled = true; })` to observe that the promise has not settled yet, then later in the same test calls `registry.close('t1', 'test over')`, which rejects that same `q.answer`. Running it should give the eight green tests Step 4 predicts.
- **Actual:** `vitest run` reports all eight assertions passing but the run itself exits 1: `Vitest caught 1 unhandled error` — `Unhandled Rejection: Error: test over`, attributed to the `close()` call. `.then(onFulfilled)` with no second argument returns a *new* promise that also rejects once the source does; `await expect(q.answer).rejects.toBeInstanceOf(TurnClosedError)` two lines later only subscribes to and handles the rejection on the *original* `q.answer`, not on the derived promise the floating `.then()` created, so that second promise's rejection is never observed by anything and Node reports it as unhandled. This is invisible from the assertion output — `Tests 78 passed (78)` reads clean — and shows up only as a separate `Errors 1 error` line and a non-zero exit code, which is exactly the signal `pnpm -r test` and CI key off.
- **Impact:** Run literally, this task would have committed a test file that reports green in isolation but fails the run, and fails the whole-workspace `pnpm -r test` the same way — the one hard, standing constraint every task in this plan carries. Not found by reading the brief; only by actually executing `vitest run` and checking its exit code rather than its assertion tally, which is precisely the FL-043 pattern repeating: the brief's own file, applied literally, does not do what it says.
- **Workaround / decision:** Gave the floating `.then()` a no-op second (rejection) handler — `q.answer.then(() => { settled = true; }, () => {})` — so the derived promise is observed and the assertion's intent (confirm the promise has not resolved yet) is unchanged. Confirmed the fix by running before and after: before, `vitest run` exits 1 with the unhandled-rejection report above; after, all nine files (81 tests, after this task's own additions) pass with exit 0 and zero unhandled errors. A parallel version of the same mistake appeared in one of my own new tests in the added `timer hygiene` block (two `ask()` calls whose returned promises were never captured), caught the same way before it was committed.
