# Friction Log

Every entry records something that did not work the way the documentation, tooling, or program said it would, what it cost, and how HomeLedger routed around it. Entries are numbered in the order they were hit. Where a friction point drove a design decision, the decision is named so the two can be read together with the [design spec](docs/superpowers/specs/2026-09-13-homeledger-design.md).

Format per entry: **Area** · **Expected** · **Actual** · **Impact** · **Workaround / decision** · **Source** · **Status**.

## Design phase (2026-09-13)

### FL-001 · Alexa+ · MCP Toolkit access is gated, and the request path is not discoverable
- **Expected:** The MCP Toolkit quickstart reads as self-serve: install `@alexa-ai/cli`, run `alexa-ai new mcp`, deploy, test in the web simulator.
- **Actual:** The docs home says the Category SDK and MCP Toolkit are "available to select partners only." The development-stages page says "you request access to the Private Preview" and links no form. The Alexa+ for Builders landing page has no request button. An established skill developer (AnyList) reported a rejected request. The Devpost organizer wrote that entrants "will have no way to actually call Alexa+ anyway."
- **Impact:** A day of reading three pages that disagree about whether a developer can start. No way to test against the real client.
- **Workaround / decision:** Build the MCP server to the published client contract and drive it from a simulated Alexa+ web experience with our own agent, which the organizer confirmed is acceptable. Design section 1 and 7.
- **Source:** https://developer.amazon.com/docs/alexaplus/add-ons/home.html · https://developer.amazon.com/docs/alexaplus/add-ons/alexa-plus-add-on-development-stages.html · https://amazonappdev2026.devpost.com/forum_topics/45058-clarification-on-simulated-alexa-web-experience-requirements
- **Status:** Open. Asked on the Devpost forum whether hackathon entrants can get dev-stage access.

### FL-002 · Alexa+ · Authentication docs contradict each other and the MCP spec
- **Expected:** One documented location for OAuth protected-resource metadata and a spec-conformant 401.
- **Actual:** The quickstart says to host metadata at `/.well-known/oauth-authorization-server`; the account-linking page says `/.well-known/oauth-protected-resource`. The auth page says 401 responses carry no `WWW-Authenticate` header and that Dynamic Client Registration, Client ID Metadata Documents, and OIDC are all unsupported, which is the opposite of the MCP 2025-11-25 authorization guidance the hackathon links.
- **Impact:** Cannot tell which discovery path a real Alexa+ client would follow.
- **Workaround / decision:** Let AgentCore Runtime own the resource-server surface. It serves protected-resource metadata and a spec-conformant 401 with `WWW-Authenticate` on its own invocation URL, so the server code does not have to pick a side. Design section 4.5.
- **Source:** https://developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-quickstart.html · https://developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-account-linking.html · https://developer.amazon.com/docs/alexaplus/add-ons/mcp-toolkit-authentication.html
- **Status:** Open. Feature request filed.

### FL-005 · MCP spec · The hackathon's minimum version and the current version disagree on fundamentals
- **Expected:** Implementing the linked 2025-11-25 Streamable HTTP page would be current.
- **Actual:** The 2026-07-28 revision removed protocol sessions and the `Mcp-Session-Id` header, removed the `initialize` handshake, replaced server-initiated elicitation with multi round-trip requests, removed SSE resumability, and moved tasks into an extension. The TypeScript SDK v2 (stable line) implements 2026-07-28; v1.x is in maintenance.
- **Impact:** A server written to the hackathon's linked pages is a legacy server on day one.
- **Workaround / decision:** SDK v2 with a modern stateless branch and a sessionful legacy branch from one server factory. Design section 4.1. Week-1 spike validates the legacy branch on AgentCore before building on it.
- **Source:** https://modelcontextprotocol.io/specification/2026-07-28/changelog · https://ts.sdk.modelcontextprotocol.io/v2/serving/legacy-clients.html
- **Status:** Resolved by decision; spike pending.

### FL-017 · MCP SDK · Elicitation spike confirms architecture A with no code changes from the documented shape
- **Expected:** A multi round-trip tool handler written once against `@modelcontextprotocol/server` (`inputRequired`/`acceptedContent`, keyed off `ctx.mcpReq.inputResponses`) would deliver `elicitation/create` to a 2026-07-28 client directly, and the SDK's documented legacy shim would deliver the same request to a 2025-era client over its `NodeStreamableHTTPServerTransport` session, without any transport- or era-specific handler code.
- **Actual:** Confirmed on both generations on the first run, with the `dev.ts`/`server.ts` code exactly as drafted (no fallback to the JSON-Schema `requestedSchema` form, no `ctx.mcpReq` field-name correction). The modern test drives `echo_confirm` through `StreamableHTTPClientTransport` from `@modelcontextprotocol/client` with `client.setRequestHandler('elicitation/create', ...)` and gets one `elicitation/create` round trip per call, matching `inputRequired.maxRounds: 3`. The legacy test drives the same tool through `createApp`'s session-based route (`src/legacy.ts`, `NodeStreamableHTTPServerTransport`) using `@modelcontextprotocol/sdk` 1.30.0's `Client` and `ElicitRequestSchema`, and the server-side default-on legacy shim (`ServerOptions.inputRequired.legacyShim`, default `true`) converted the same `inputRequired(...)` return into a real server→client `elicitation/create` request over the session, re-entering the handler with the answer on retry — with zero legacy-aware code in `dev.ts`. Versions: `@modelcontextprotocol/server` 2.0.0, `@modelcontextprotocol/client` 2.0.0, `@modelcontextprotocol/sdk` 1.30.0 (`pnpm ls @modelcontextprotocol/server @modelcontextprotocol/sdk`).
- **Impact:** None — this is the positive result the whole Plan 1 architecture (and Plan 2's `book_service`) is staked on: one handler, one code path, both client generations, including decline handling (no re-ask) and the `devTools` gate.
- **Workaround / decision:** None needed. Architecture A stands as designed; no addendum task to build a v1-flavoured `server-v1.ts` fallback (architecture C) is opened.
- **Source:** `apps/mcp-server/src/tools/dev.ts` · `apps/mcp-server/test/elicit-modern.test.ts` · `apps/mcp-server/test/elicit-legacy.test.ts` · `node_modules/@modelcontextprotocol/server/dist/createMcpHandler-CLhGwQTn.d.mts` (`ServerOptions.inputRequired`, `inputRequired`, `acceptedContent`) · `node_modules/@modelcontextprotocol/client/dist/index.d.mts` (`ClientOptions.inputRequired`, `.versionNegotiation`)

### FL-018 · Terraform CLI · `output -raw` exits 0 with a warning when the state has zero outputs, not just when one output is missing
- **Expected:** The deploy workflow's bootstrap guard, `if ! terraform output -raw ecr_repository_url >/dev/null 2>&1; then <targeted apply>; fi`, would fail (non-zero exit) on a brand-new state that has never been applied, so the guard's `then` branch would run and create the ECR repository the image build depends on.
- **Actual:** On a state with zero outputs defined at all (nothing has ever been applied), `terraform output -raw NAME` prints `Warning: No outputs found` to stderr and exits **0**, the same as a successful lookup — it does not exit non-zero the way it does when the state has *other* outputs but not the named one. Run 34882037117 hit exactly this: the guard's condition was true (`>/dev/null 2>&1` succeeded), so the bootstrap `terraform apply -target=aws_ecr_repository.mcp ...` was skipped entirely. Nothing was created — no ECR repository, no state object, no table. The next step, `REPO=$(terraform -chdir=infra/live/demo/platform output -raw ecr_repository_url)`, then also printed the same warning and captured an empty string, and `scripts/build-image.sh` failed immediately with `line 3: 1: usage` because `REPO_URL="${1:?usage: build-image.sh <ecr-repo-url> [tag]}"` saw an empty positional argument.
- **Impact:** The entire first deploy run failed at "Build and push image" before any AWS resource existed; the apply job never reached `terraform apply` for the full plan.
- **Workaround / decision:** Replaced the exit-code guard with a state-membership check, `if ! terraform state list 2>/dev/null | grep -qx 'aws_ecr_repository.mcp'; then <targeted apply>; fi`, which only depends on whether the resource is actually in state and is unaffected by `output`'s exit-code behavior. Also set `terraform_wrapper: false` on every `hashicorp/setup-terraform@v3` step in `deploy.yml` so later `$(terraform output -raw ...)` captures (image repo URL, invocation URL, Cognito values) are reading Terraform's own stdout directly rather than through the wrapper's JSON-log proxy.
- **Source:** https://github.com/jkarns87/homeledger/actions/runs/34882037117 · https://developer.hashicorp.com/terraform/cli/commands/output
- **Status:** Resolved.

### FL-019 · AWS account · Bedrock reported suspended after new-account verification failed
- **Expected:** After account creation on 2026-09-14 and the morning's verification hold clearing (first invocations of Claude Sonnet 4.6, Nova Lite, and Titan Embeddings v2 all succeeded that afternoon), Bedrock would stay available for the hackathon build.
- **Actual:** AWS notified that new-account verification failed and that Bedrock was suspended on account `<account-id>` the same day. Support case 178941623300459 was opened at 2026-09-14T20:03Z as the root user under Account → Other Account Issues; the Basic support plan only allows severity "General question", so no expedited path exists. At about 20:15Z, root-session checks still returned completions from `us.amazon.nova-lite-v1:0` and `us.anthropic.claude-sonnet-4-6`, and the AgentCore control plane listed runtime `demo_homeledger_mcp` as READY, so the scope or timing of the suspension is unclear from the API side. At about 20:35Z the same checks run from GitHub Actions as the OIDC deploy role (run 34894134737) also succeeded for both models and listed the runtime READY, so no principal was observed blocked at that time.
  Two days later the block was confirmed, and it is narrower than "Bedrock is suspended" suggests. On 2026-09-16 the same deploy-role probe (run 35103741472) returned, for BOTH models, `ValidationException ... Error 002: Access to Bedrock models is not allowed for this account`, while the AgentCore control plane in the same run still listed `demo_homeledger_mcp` as READY. So the restriction applies to model invocation only: the AgentCore data plane, DynamoDB, Cognito, ECR, S3, and IAM are all unaffected, and the deployed MCP server keeps serving every tool that does not call a model. The suspension therefore took effect some time AFTER 2026-09-14T20:35Z, which is why the probes that evening came back clean.
  Re-probed a second time the same day at 2026-09-16T17:21Z (run 35127676347) to check whether the block was transient. It is not: both models returned the byte-identical `Error 002` string, and `demo_homeledger_mcp` was still READY in the same run under the same role. Two independent probes hours apart, identical results, so the state is stable rather than flapping — worth knowing before spending any more time re-checking, and the reason the remaining blocked work is deferred rather than retried on a timer.
- **Impact:** Narrower than first feared, and narrower again than this entry originally said — **creating the Knowledge Base was never blocked.** The module applied cleanly on the first post-merge deploy of Plan 2 (merge `0174612`): bucket, Knowledge Base, data source, S3 Vectors index, and IAM role all exist, because nothing in the apply path invokes a model. What is blocked is the ingestion job, whose first act is to have the Knowledge Base role call the Titan embedding model. FL-032 records that correction and what it cost. Blocked: running an ingestion job, `ask_manual` against a populated index, the Strands agent in the simulator, and Nova vision for snapshot descriptions. NOT blocked: every tool the deployed server exposes today, the entire in-memory development path, all Terraform authoring and offline validation, and the Bedrock adapter itself, which is unit-tested against a stubbed sender rather than a live call. Submissions close 2026-10-23 and judging runs 2026-11-09 to 2026-11-20, and the organizers expect resources to be live only for test windows, so an outage in mid-September costs nothing provided it clears before the video and the judging window.
- **Workaround / decision:** Keep building. The design already isolates every model call behind an interface with an in-memory implementation — `ManualRetriever` has a fixture adapter, the repository has an in-memory twin — so development continues at full speed without Bedrock. Only two things wait on it: the manuals ingestion run and the smoke assertion that `ask_manual` returns a real passage. The Knowledge Base apply was listed here as a third and should not have been — it went through on the first attempt (FL-032). Re-probe with the `aws-oidc-check` workflow rather than a local session, since that path needs no local credentials and survives session expiry. If the case stalls, aws-verification@amazon.com is the address AWS's own verification error names. Note that case status cannot be read via the Support API at all on a Basic support plan, so the console is the only view.
- **Source:** AWS Support case 178941623300459 · https://github.com/jkarns87/homeledger/actions/runs/34890188789 (smoke run during the report) · https://github.com/jkarns87/homeledger/actions/runs/34894134737 (deploy-role probe, clean) · https://github.com/jkarns87/homeledger/actions/runs/35103741472 (deploy-role probe, block confirmed) · https://github.com/jkarns87/homeledger/actions/runs/35127676347 (deploy-role probe, block stable on re-check)
- **Second-order friction — the case is unreadable to the tooling that needs it.** Confirming the block took one dispatched workflow and about ninety seconds. Confirming whether AWS has *acted* on it is not possible from any automated path: the Support API requires a Business or Enterprise plan and the account is on Basic, so `aws support describe-cases` is unavailable at exactly the severity tier where a blocked builder most needs it. The deploy role deliberately carries no `support:*` permission, and widening a CI role's blast radius permanently to read one case was rejected as a bad trade. So the loop is asymmetric: the machine can verify the symptom indefinitely but a human must open the console to learn the cause's status. For a hackathon on a new account — precisely the population most likely to trip new-account verification — that asymmetry is the friction, more than the block itself.
- **Status:** Open, confirmed, and stable across two independent same-day probes. Model invocation is refused account-wide; everything else works. Build continues on the in-memory paths. Not re-probing on a schedule: two probes hours apart returned identical errors, so further polling buys nothing until the case moves, and the case's movement is only visible in the console.

### FL-020 · AgentCore Runtime · The Host header the platform forwards is undocumented, and the server's host allowlist rejects it
- **Expected:** The MCP protocol contract says the container listens on `0.0.0.0:8000/mcp`. Either the platform's requests would carry a Host the SDK's default allowlist accepts (`localhost`, `127.0.0.1`, `0.0.0.0`), or the contract would name the Host value a server must allow.
- **Actual:** With a valid Cognito token, every request through the invocation URL returns JSON-RPC `-32010 Received error (403) from runtime. Please check your CloudWatch logs`, and the runtime log shows only clean `listening` lines because the SDK rejects without logging. Locally, the same server answers `403 {"code":-32000,"message":"Invalid Host: <host>"}` to any Host outside `ALLOWED_HOSTS`, so the platform forwards a Host value the allowlist does not contain. The contract page does not state what Host AgentCore sends.
- **Impact:** Smoke run 34890188789 failed at the first `tools/list`; no tool call has completed through AgentCore yet, although the runtime deployed and reached READY on the first successful apply (run 34883140640).
- **Workaround / decision:** Final state: disable Host-header validation entirely for the deployed runtime rather than pin the observed hostname. `@modelcontextprotocol/express`'s `createMcpExpressApp` only installs its `hostHeaderValidation` middleware when `allowedHosts` is passed; `apps/mcp-server/src/app.ts` now accepts `opts.allowedHosts = 'any'` and, in that case, omits the option from `createMcpExpressApp` (not merely an empty/guessed list). `apps/mcp-server/src/index.ts` maps `ALLOWED_HOSTS="*"` to `'any'`; unset keeps the local default list (`localhost,127.0.0.1,0.0.0.0`), preserving DNS-rebinding protection for local runs. `infra/live/demo/platform`'s `allowed_hosts` variable now defaults to `"*"`. This is correct rather than a weakening: under AgentCore Runtime the container is reachable only through the authenticated invocation endpoint, so the JWT authorizer (`custom_jwt_authorizer`, `allowed_clients`) is the actual access control there, and no fixed hostname allowlist can be relied on against an internal, undocumented, apparently cell-specific value that AWS does not document and could change. The two intermediate guesses tried first — `bedrock-agentcore.us-east-1.amazonaws.com` (the public invocation host, insufficient: smoke run 34904655264 still 403'd) and then the observed `cell01.us-east-1.prod.arp.kepler-analytics.aws.dev` (found by adding a one-line `request-rejected` log in `app.ts`, since the SDK's host check runs ahead of any middleware added inside `createMcpExpressApp`'s app — surfaced on smoke run 34905897848 via CloudWatch, confirmed working on smoke run 34906755556) — are recorded here for the record but superseded by the `"*"` fix. ### FL-032 · Bedrock Knowledge Base · A Knowledge Base provisioned under an account-level model block cannot ingest OR retrieve, because query embedding needs the same model — so infrastructure-as-code reports success for a resource that cannot do its job at all
- **Expected:** Two things, both wrong. First, per FL-016 and FL-019, that the Knowledge Base apply was itself blocked — every earlier entry, several code comments, and the README all assumed "Bedrock is blocked" meant the `aws_bedrockagent_knowledge_base` resource could not be created, which is why the module was described as "authored, never applied" and the smoke's `KNOWLEDGE_BASE_ID` was expected to stay empty. Second, that `KNOWLEDGE_BASE_ID` being non-empty is a sufficient test for "real retrieval is available," which is the assumption both skip paths were built on.
- **Actual:** Plan 2 merged as `0174612` and `deploy.yml` applied cleanly, Knowledge Base module included. The S3 manuals bucket, the Bedrock Knowledge Base, and the knowledge-base IAM role all exist. The apply was never blocked. **That corrects the record in FL-016 and FL-019, and it is now proven rather than assumed** — the control plane creates the Knowledge Base, its data source, and the S3 Vectors index without ever invoking a model, so nothing in the apply path touches the thing the account block refuses.
  The block moves one step later, to the first operation that does invoke a model. Smoke run 35238251562 failed at `seed:manual`: the S3 upload of the fixture PDF and its `.metadata.json` sidecar succeeded, and `StartIngestionJob` then returned `ValidationException ... Knowledge base role arn:aws:iam::<account>:role/demo-homeledger-knowledge-base is not able to call specified bedrock embedding model arn:aws:bedrock:us-east-1::foundation-model/amazon.titan-embed-text-v2:0: Error 002: Access to Bedrock models is not allowed for this account (Service: BedrockRuntime, Status Code: 400)`, HTTP 400. Starting an ingestion job makes the Knowledge Base role call Titan to embed, and that invocation is refused by the same account-wide block FL-019 records (support case 178941623300459, still unresolved). Note the `Error 002` string is byte-identical to the one the deploy-role probes returned in FL-019 — same block, reached through a different caller.
  So a Bedrock Knowledge Base under an account-level model block is **provisioned, addressable, referenced by the runtime, and permanently empty.** `terraform apply` is green, `terraform output -raw knowledge_base_id` returns a real id, the AgentCore runtime carries that id in its environment, and not one document can ever be embedded into it.
- **Impact:** The damage was not the failed ingestion — that was expected collateral of FL-019. The damage was that **one blocked embedding call hid all eight working tools.** Both skip paths in this repo keyed off a binary "is a Knowledge Base provisioned," read as `KNOWLEDGE_BASE_ID != ''`: the workflow used it to decide whether to run `seed:manual` at all, and `scripts/smoke.ts`'s `checkManualPassages` used it to decide whether to enforce the `ask_manual` assertion. With the Knowledge Base now provisioned, that condition is true, so neither skip fired; `seed:manual` exited 1 on the `StartIngestionJob` rejection, the step failed, and the workflow never reached `Run smoke`. Tool order, widget wiring, the FL-023 appliance-count guard, elicitation through the legacy shim, three-round `book_service`, progress notifications, `get_visit` — none of it ran. A run that should have proved eight of nine tools healthy proved nothing at all, and the first post-merge signal on a working deploy was a red X.
  The general finding, and the reason this is worth a friction entry rather than a bug fix: **"is it provisioned" is the wrong abstraction.** Provisioning and usability are separate properties, and infrastructure-as-code only reports the first. Any resource whose usefulness depends on a capability outside its own creation path — a Knowledge Base that needs model invocation, a KMS-encrypted bucket whose key policy is managed elsewhere, a VPC endpoint whose service is not enabled in the account, a queue subscribed to a topic in a suspended region — can be created successfully and still be incapable of its job. Tooling that models two states (absent / present) has nowhere to put the third (present but unusable), and the failure mode is not a wrong answer but no answer: the check that was supposed to degrade gracefully instead takes down everything downstream of it.
- **Workaround / decision:** Model the third state explicitly, in both places it bites, without weakening either real guard.
  1. `scripts/manuals.ts` grew `isBedrockAccountBlock(error)`, which requires all three of: `name === 'ValidationException'`, `$metadata.httpStatusCode === 400`, and a message containing the exact sentence `Access to Bedrock models is not allowed for this account`. Duck-typed on `name` rather than `instanceof`, per AWS's own v3 error-handling guidance, since each client bundles its own copy of the exception class. The sentence is the match because it is the only part of the message that states the condition; the role ARN, the model ARN, the `Error 002` code, and the `(Service: ..., Status Code: ...)` suffix are all excluded deliberately as account-, model-, region- and wrapper-specific noise that would make the matcher break on changes unrelated to the condition. It is scoped to the `StartIngestionJob` call only — not to terminal `FAILED` statuses, and explicitly **not** a blanket catch of `ValidationException`, which `StartIngestionJob` also raises for a malformed metadata sidecar, an S3 key outside the data source's inclusion prefix, and a `dataSourceId` that does not belong to the knowledge base. All of those are real bugs in this repo and all still fail the run. On a match `uploadManual` returns a discriminated `{ ingestion: 'skipped-bedrock-blocked' }` result, `seed:manual` prints a loud banner plus a bare `MANUAL_INGESTION_SKIPPED` sentinel line, and exits 0.
  2. The uploaded S3 objects and the `DOC#` row are **kept, not rolled back.** The PDF and its sidecar are exactly the input a later ingestion job consumes, so once the block clears a bare `StartIngestionJob` picks them up with no re-upload; the `DOC#` row is what `get_appliance` reads for `{docId, title}` and what `appliance.manualDocId` points at, so deleting it would remove working functionality in reaction to an unrelated external outage. The row stays honest — `kbSync.status` is left at `'pending'` with `at: null`, which is the accurate description of uploaded-but-not-ingested, and is why this is kept state rather than orphaned residue. Contrast the appliance-not-found guard in the same function, which deliberately writes nothing because that error is permanent and operator-caused; this one is transient and external. `derivedId` keeps `docId` and `s3Key` deterministic, so a re-run replaces in place — the duplicate-accumulation risk that would otherwise argue for cleanup does not exist here.
  3. `scripts/smoke.ts`'s `checkManualPassages` now returns one of three outcomes instead of two. The distinction that matters is between "ingestion was skipped" and "ingestion happened and returned the wrong content," and **those are indistinguishable from the retrieval side by construction** — a never-ingested Knowledge Base and a runtime quietly serving `SAMPLE_MANUAL_PASSAGES` both come back as "no passage carries `SMOKE_MANUAL_TITLE`." Inferring the skip from an empty or fixture-shaped result would therefore reintroduce exactly the false green the assertion exists to prevent. The signal is instead carried in from the step that knows: `.github/workflows/smoke.yml` greps `^MANUAL_INGESTION_SKIPPED$` out of the seed step's log and exports `MANUAL_INGESTION_SKIPPED=1`, the same log-sentinel idiom as the `grep -q '^SMOKE OK$'` gate. `manualIngestionSkipped()` accepts only `1`/`true`/`yes`, so unset, empty, `0`, `false`, and anything unrecognised all mean "enforce" — the skip is opt-in by exact value, and a mistyped signal produces a red pipeline rather than a green one that proves nothing.
  4. `continue-on-error` was explicitly **not** used as the mechanism on the seed step. It would have swallowed the malformed-sidecar, bad-key, missing-data-source, and unrelated-IAM cases alongside the one condition worth tolerating, which is the opposite of the point. The step is a plain `run:` under bash's `-eo pipefail`, so any non-zero exit from `seed:manual` still fails the job.

  The cause is the part of Bedrock retrieval that is easy to forget: **`Retrieve` embeds the QUERY, not just the documents.** The question has to become a vector before it can be compared against the index, and that embedding call goes to the same Titan model the account block refuses. So the block does not merely leave the Knowledge Base empty — it makes the Knowledge Base **unqueryable**. There is no "degraded but working" mode: `Retrieve` fails server-side against a Knowledge Base that exists, is correctly configured, holds a valid (if empty) S3 Vectors index, and is wired into the runtime. `createKnowledgeBaseRetriever` calls `sender.send` bare (`packages/core/src/retrieval/bedrock.ts`), `ask_manual` does not catch it either (`apps/mcp-server/src/tools/manual.ts`), so the throw reaches the MCP SDK, which converts a thrown handler into `{ isError: true, content: [...] }` with **no `structuredContent` at all** — and the smoke dereferenced it blindly.

  That corrects the model in this entry's own workaround section. The fix modelled three states and named the third "Knowledge Base provisioned, but ingestion impossible." Reality has a fourth, and it is the one that actually obtains today: **Knowledge Base provisioned, but the Knowledge Base cannot be used at all.** "Provisioned but empty" turns out to have been an optimistic reading of "provisioned but unusable" — we assumed the read path would still function and return nothing, and it does not function at all. Two rounds of this now: each time the binary abstraction was refined, the refinement was still one step short of how far the failure actually propagates.

  **The generalisation, and the bit worth taking away from the whole entry:** a capability dependency does not stop at the operation that obviously needs it. Embedding is required by ingestion *and* by query, so one blocked model invalidates both halves of a resource that reports itself healthy on every control-plane API. When a resource depends on a capability outside its own creation path, the right question is not "which operation needs it" but "how far does that dependency reach" — and the honest answer is usually further than the first failing call suggests. A health check that models *provisioned / not provisioned* cannot express this; neither can one that models *provisioned / empty / populated*. What the tooling actually has to model is whether each **operation** is available, which is a property of the account and the moment, not of the resource.

  Second-order cost, and the reason this one belongs in the log rather than a commit message: the crash was a `TypeError` from a property access, which tells an operator nothing about the system under test and stops every later assertion from running. The smoke had already proved six things about the deployed runtime and was about to prove eight more through the legacy client; a raw dereference threw all of it away and reported a line number. A smoke script must always end in a sentence that names what went wrong or a sentence that says why it was skipped — never a stack trace.
- **Second fix (branch `fix-smoke-ask-manual-error-result`).** Two changes, deliberately separable. (1) **Robustness, independent of Bedrock:** `readManualResult` classifies an `ask_manual` result without dereferencing anything that may be absent — it is total over `undefined`, `null`, a string, `isError: true`, a missing/`null`/non-object `structuredContent`, and a `passages` that is not an array, and every one of those maps to a described error rather than a throw. `firstTextBlock` does the same for the content array, closing an identical latent crash in the `assertSpokenProse` call (`(undefined as unknown[])[0]` throws; the old `?.` was reassurance one level too late). `assertManualPassages` was hardened the same way, so a malformed passage fails the MATCH instead of crashing the comparison. Everywhere else an error result **throws**, including when no Knowledge Base is configured at all, since the runtime serves in-memory fixtures in that state and has nothing that can legitimately error. The error branch is evaluated FIRST and gated on `ingestionSkipped` specifically so the tolerance cannot be reached by any other path.
